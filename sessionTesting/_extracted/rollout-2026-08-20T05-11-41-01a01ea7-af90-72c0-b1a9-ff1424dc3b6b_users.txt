1. **The workbench state model needs concurrency protection before delegation becomes highly parallel.** `load_run()` reads `manifest.json`, individual commands mutate that snapshot, and `save_run()` atomically replaces the file—but there is no lock, revision check, or compare-and-swap. Two concurrently completing agents can therefore both load revision N, independently append their state, and whichever saves last can erase the other's manifest update. The event log and individual task files are also updated separately from the manifest, so a crash can leave the three representations disagreeing. Atomic file replacement protects against torn JSON, but not lost updates or cross-file transactional inconsistency.

   This may never occur while Codex serializes all workbench operations, but it is at odds with the system's eventual multi-agent purpose. I'd either add repository/run locking now, or move toward an append-only canonical event ledger from which compact manifests are derived/rebuilt.

2. **Muse delegation needs an explicit job protocol rather than directory inference.** Right now `delegate-muse` snapshots the `.codex/muse/jobs` directory before launch, blocks on the runner, compares directory names afterward, and assumes the lexically last newly created directory is the job. More importantly, a zero exit code marks the task `completed` even if no job directory, manifest, or result exists.

   That is currently the weakest integration seam in the package.

   I'd have Codex define a tiny versioned contract such as:

   ```text
   runner start → immediately returns job_id + manifest path
   runner status <job_id>
   runner result <job_id>
   runner cancel <job_id>
   ```

   Then the workbench records the job ID **before** waiting. This also fixes a second issue: if `delegate-muse` is interrupted after setting the task to `running`, the outer `KeyboardInterrupt` handler exits without discovering or linking the durable Muse job. A durable underlying worker deserves a durable orchestration binding.

3. **Context packets need provenance about incompleteness.** The bounded-context idea itself is good. But if a selected file exceeds the remaining byte budget, the workbench reads only the prefix and inserts it under `## File: path` without saying the file was truncated. A nonexistent `--include` path is also silently ignored.

   That's dangerous specifically because these packets are meant for delegated reasoning. A worker can reasonably interpret:

   ```text
   ## File: src/foo.py
   ...
   ```

   as “this is `src/foo.py`,” not “this is the first 37% of `src/foo.py`.”

   I would record for every requested input:

   ```text
   requested
   found/missing
   total bytes
   supplied bytes
   complete/truncated
   content hash
   ```
